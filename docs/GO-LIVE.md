# Go-Live Guide — Care 1-to-1 Hours Tracker

Production deployment for company use.

- **Database:** Neon (serverless Postgres)
- **App (frontend + backend):** Render — one Docker Web Service serving the API (`/api/*`) and the built React SPA from the same origin
- **Domain:** `rightcareservices.co.uk` (owned, DNS on IONOS) → Render, with automatic HTTPS

Because the browser talks to a **single origin**, the `sameSite=lax` refresh-token cookie works with no CORS configuration and there is no client-side API URL to configure — the SPA calls `/api/*` relatively.

> This guide supersedes the quick-start in `DEPLOYMENT.md` for a real production go-live. The main differences: paid plan (no cold starts), real login accounts instead of the seeded test passwords, AI env vars, and the custom-domain DNS.

---

## 0. Pre-flight (do this first)

Your deployment files are currently **uncommitted**. Render builds from the Git repo, so nothing deploys until these are pushed:

```bash
git status                       # DEPLOYMENT.md, render.yaml, apps/server/src/index.ts, apps/server/src/db/migrate.ts
bun install && bun run typecheck && bun test   # sanity-check the build is green
git add -A && git commit -m "Deployment config for production"
git push origin master
```

Also confirm the repo is pushed to GitHub/GitLab and that Render will have access to it (you connect the account in step 2).

Decide the region up front: you're a UK company, so keep **both** Neon and Render in the **EU (Frankfurt)** region to minimise latency and keep data in the EU.

## 1. Database — Neon

1. Create an account at https://neon.tech and a new **project** in region **EU (Frankfurt)**.
2. In the project, open **Connection Details** and copy the **pooled** connection string — the host contains `-pooler`. Make sure it ends with `?sslmode=require`:

   ```
   postgresql://user:pass@ep-xxxx-pooler.eu-central-1.aws.neon.tech/neondb?sslmode=require
   ```

   Use the **pooled** string (not the direct one) — the app runs on a serverless-style platform and opens/closes connections, which the pooler handles far better.
3. Keep this string secret; you'll paste it into Render as `DATABASE_URL` (never commit it).

> **Free vs paid:** Neon's free tier auto-suspends the database after inactivity, adding a cold-start delay to the first request. For company use, the Neon **Launch** plan (or keeping the free project but accepting the occasional cold start) is fine to start — you can upgrade later without changing the connection string.

## 2. App — Render Web Service

You can deploy via the committed `render.yaml` Blueprint or create the service manually. **Blueprint is easiest:**

1. Render dashboard → **New → Blueprint** → connect your Git provider → pick this repo. Render reads `render.yaml` and proposes the `care-tracker` web service.
2. It will prompt for the env vars marked `sync: false` — fill in `DATABASE_URL` (step 1). `JWT_SECRET` is auto-generated by the Blueprint.
3. Before the first deploy, set the plan and region (see below) and add the remaining env vars (step 3).

**Manual alternative:** New → Web Service → **Docker**, point at the repo, Dockerfile `./Dockerfile`, health check path `/health`.

### Plan & region

| Setting | Value | Why |
|---|---|---|
| Region | Frankfurt (EU) | Same region as Neon; UK data residency |
| Instance type | **Starter ($7/mo) or higher** | The free plan sleeps after ~15 min idle — a several-second cold start every morning is a bad experience for care staff. Starter stays warm. |
| Health check path | `/health` | Returns `{"status":"ok","db":"up"}` |

> **Migrations run automatically at container startup** in production (`apps/server/src/index.ts` → `runMigrations()`), because Render's free plan ignores `preDeployCommand`. This is idempotent and safe. On a paid plan you *may* move migrations to a pre-deploy step by uncommenting `preDeployCommand: bun run db:migrate` in `render.yaml` and removing the startup call — but leaving it as-is also works fine.

## 3. Environment variables (Render → service → Environment)

| Key | Value | Required |
|---|---|---|
| `NODE_ENV` | `production` | ✅ (set by Blueprint) |
| `JWT_SECRET` | 64-hex secret — `openssl rand -hex 32` | ✅ (Blueprint auto-generates) |
| `DATABASE_URL` | Neon **pooled** string from step 1 | ✅ |
| `OPENAI_API_KEY` | Your OpenAI key (`sk-...`) | ⚠️ Only if you want the AI features |
| `ACCESS_TOKEN_TTL` | e.g. `15m` (default) | optional |
| `REFRESH_TOKEN_TTL_DAYS` | e.g. `30` (default) | optional |
| `AI_POLISH_MODEL` | default `gpt-4.1-nano` | optional |
| `AI_TRANSCRIBE_MODEL` | default `gpt-4o-mini-transcribe` | optional |

**About the AI key:** the app has two OpenAI-powered features — "polish activity record" and speech-to-text dictation on the staff recording page. `OPENAI_API_KEY` is **optional**: if it's absent the endpoints return `503` and the rest of the app works normally (the buttons just won't do anything). If your staff will use dictation/polish, add the key and set a spend limit on the OpenAI account. If not, leave it unset.

`PORT` is injected by Render automatically — don't set it.

## 5. Create real login accounts (do NOT ship the seed passwords)

⚠️ **Important for a real company deployment.** The `bun run db:seed` command creates convenience accounts with **publicly-known passwords** (`manager@example.com` / `Password123!`, etc., and an admin `chris_admin@carecompliance.com` / `Password123#`). These are **test-only** and must never be usable in production.

You have two safe options:

**Option A — seed, then immediately lock down (simplest):**
1. Open the Render **Shell** for the service and run once:
   ```bash
   bun run db:seed        # idempotent: creates activity list, compliance defaults, sample data + the test accounts
   ```
2. Log in as the manager/admin, then in the admin **user management** UI: create your real staff/manager/auditor accounts with strong passwords, and **delete or deactivate every seeded test account** (`manager@example.com`, `staff@example.com`, `auditor@example.com`, `chris_admin@carecompliance.com`). Deactivating a user also revokes their refresh token, so their access ends immediately.
3. Also remove the seeded **sample service users / week plans** so the app starts clean for real data.

**Option B — seed reference data only, skip test accounts:**
The seed also inserts the **activity list** and **compliance settings** which you *do* want. If you'd rather not create the test accounts at all, tell me and I'll add a `db:seed --no-users` flag (or a separate `db:seed:reference` script) so you get activities + compliance defaults without any known-password logins, then create your first admin via a one-off script.

> Recommendation: **Option A** to get moving, and make deleting the test accounts the very next step — before you point the domain at it. If you'd prefer Option B for a cleaner audit story, say so and I'll wire up the flag.

## 6. Custom domain — `rightcareservices.co.uk` via IONOS

Render issues free, auto-renewing Let's Encrypt TLS certificates once DNS is verified.

### 6a. Add the domains in Render
Service → **Settings → Custom Domains → Add**:
- `www.rightcareservices.co.uk`
- `rightcareservices.co.uk` (apex/root)

Render will show the exact DNS targets and mark each domain "unverified" until DNS propagates. Pick one as **primary** (recommended: `www`) — Render auto-redirects the other to it.

### 6b. Configure DNS at IONOS
Log in to IONOS → **Domains & SSL → rightcareservices.co.uk → DNS**. Add/edit these records (delete conflicting existing A/CNAME records for `@` and `www` first, e.g. any IONOS parking page):

| Type | Host/Name | Value | Notes |
|---|---|---|---|
| **CNAME** | `www` | `care-tracker-xxxx.onrender.com` | Use the exact `.onrender.com` host Render shows you |
| **A** | `@` (root) | `216.24.57.1` | Render's apex anycast IP — confirm the current value in Render's dashboard, it's shown next to the apex domain |

IONOS doesn't support `ALIAS`/`ANAME` on the root, so the apex uses Render's documented **A record IP**. Always use whatever IP/host Render displays for your service rather than assuming — Render occasionally updates them.

If IONOS is only acting as registrar and you'd rather manage DNS elsewhere, you can point the nameservers at another provider, but editing the records above directly in IONOS is simpler.

### 6c. Wait & verify
- DNS propagation is usually minutes but can take up to a few hours. Check with:
  ```bash
  dig +short www.rightcareservices.co.uk
  dig +short rightcareservices.co.uk
  ```
- When Render shows both domains **Verified** with a green certificate, open `https://rightcareservices.co.uk` and `https://www.rightcareservices.co.uk` — both should load the app over HTTPS, and the non-primary should redirect to the primary.

No app config change is needed for the domain: the SPA and API share the origin, and the refresh cookie is `secure` + `sameSite=lax`, which works correctly over HTTPS on the custom domain.

- [ ] Log out invalidates the session (refresh token revoked)

## 8. Post-launch operations

- **Backups:** Neon keeps point-in-time history (retention depends on plan). For compliance data, confirm the retention window on your Neon plan and consider periodic `pg_dump` exports to your own storage.
- **Secrets rotation:** `JWT_SECRET` can be rotated in Render (all users must re-login after). Rotate the OpenAI key from the OpenAI dashboard if leaked.
- **New schema changes:** locally run `bun run db:generate`, commit the SQL under `apps/server/drizzle/`, push — the next Render deploy applies it on boot. Never edit the DB by hand.
- **Cost watch:** set a hard spend limit on the OpenAI account; Render Starter + Neon are flat/low monthly.
- **Monitoring:** Render's health check + logs cover liveness. Consider a free uptime pinger (e.g. UptimeRobot) hitting `/health` if you want alerting.
